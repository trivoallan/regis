> handoff. The T1 measurement (below) showed that approach captures the smallest slice of
> the real cost. **Chosen approach: a single shared image pull via a local OCI layout,

## Problem Statement

`regis analyze` pulls every target image **once per image-reading tool**: syft
(`generate_sbom`), grype (`scan_vulnerabilities`), trufflehog (`scan_secrets`), and dockle
(`audit_image`) each shell out and pull the full image independently. On a large image
that is four full pulls of the same bytes. Part 1 deduped the _regctl inspector_ calls
(manifest/blob/tags) but not the scanner pulls — those go through `ToolRunner`.

Matters for the observe-first rollout: a central scan over 100+ images pays 4× the image
bytes per image, and concurrent pulls contend for bandwidth.

- `regis/core/domain/analyzers/sbom.py:131` — `ctx.tools.generate_sbom(ctx.image)` → `syft <image>`.
- `regis/core/domain/analyzers/cve.py:96` — `ctx.tools.scan_vulnerabilities(ctx.image)` → `grype <image>`.
- `regis/adapters/driven/tools/subprocess_tool_runner.py:40-51` — cve/sbom/secrets/audit each pull.

## T1 Measurement — executed 2026-06-25 (python:3.12, debian, linux/arm64)

Real `regis analyze -a cve -a sbom -a secrets -a dockle`:

| config                        | wall-clock | per-analyzer (parallel)                           |
| ----------------------------- | ---------- | ------------------------------------------------- |
| 4 workers (parallel, default) | **72.9s**  | cve 53.1 · sbom 46.0 · secrets 25.8 · dockle 12.2 |
| 1 worker (sequential)         | 102.9s     | —                                                 |

Isolated tool timings (sequential, full bandwidth each):

| invocation                          | wall-clock |
| ----------------------------------- | ---------- |
| syft \<image\> (pull + catalog)     | 34.7s      |
| grype \<image\> (pull + DB + match) | 30.4s      |
| grype `sbom:` (DB + match, no pull) | 7.4s       |
| trufflehog \<image\> (pull + scan)  | 18.3s      |
| dockle \<image\> (pull + audit)     | 13.4s      |

**Verified minimal-C primitive** (the chosen mechanism):

| step                                                                  | wall-clock | result                                       |
| --------------------------------------------------------------------- | ---------- | -------------------------------------------- |
| `regctl image copy --platform linux/arm64 python:3.12 ocidir://<dir>` | **9.58s**  | one pull, leaner than syft/grype's own       |
| `syft oci-dir:<dir>` (no pull)                                        | 15.25s     | 477 components                               |
| `grype oci-dir:<dir>` (no pull)                                       | 20.61s     | **365 CVEs = identical to grype\<image\> ✓** |

→ syft+grype pair projected at **export 9.58 + max(15.25, 20.61) parallel ≈ 30s** vs today's
~53s contended pair; removes 2 of 4 concurrent pulls.

### What the measurement established

1. **Pull dominates — confirmed.** grype's match-only is 7.4s; with the pull it is 30–53s.
2. **The "double pull" was never serial wall-clock.** Analyzers run in a 4-worker pool, so
   redundant pulls run _concurrently_; the cost is **bandwidth contention** (parallel
   per-tool times are 1.4–1.7× the isolated times). The lever is _fewer concurrent pulls_.
3. **Pull is spread across all four tools** (cve, sbom, secrets, dockle each pull).
4. **The SBOM-handoff (old Approach A) removes only 1 of 4 pulls and serializes grype
   behind syft** — smallest slice, and `grype oci-dir:` shows grype re-catalogs anyway.
5. **A shared local pull removes 2-of-4 (syft+grype) cleanly** and is the right primitive
   for the 100+-image central scan's bandwidth budget.

Format parity (apk + dpkg-slim + dpkg-large) is settled-identical, so format is a build-time
regression guard, not a discovery risk.

## Premises

1. **Image pull dominates scanner cost — MEASURED true** (grype 7.4s match vs 30–53s with pull).
2. **The cost is concurrent-pull bandwidth contention, not serial wall-clock** — so the fix is
   reducing the _number_ of pulls, not de-serializing a pair.
3. **Per-run, thread-safe, lazy memo** is the sharing mechanism — same pattern as part 1's
   `CachingImageInspector`. ✅
4. **Platform fidelity:** the export pins `--platform`; both tools read that one-platform
   layout, so they are guaranteed consistent (stronger than today's independent `--platform`).

## Approaches Considered

### Approach A: syft→grype SBOM handoff — REJECTED by T1

Generate the SBOM once, feed grype `grype sbom:`. Removes only grype's pull (1 of 4),
serializes grype behind syft, needs dual-format syft + integrity guard. The measurement
showed it is the smallest slice and largely subsumed by a shared pull.

### Approach B: opportunistic non-blocking share — REJECTED

Racy benefit under the ThreadPoolExecutor; usually pulls twice anyway.

### Approach C: full local layout for ALL four tools — DEFERRED (follow-up)

Pull once, point syft+grype+trufflehog+dockle at the local layout. Biggest win (3 of 4
pulls removed) but L/XL: dockle needs `--input <tar>` and trufflehog needs a
`docker-archive`/filesystem source — four different local-input mechanisms. Deferred until
the syft+grype primitive is in and the trufflehog/dockle local-input is verified.

### Approach D: shared local OCI pull for syft+grype — **CHOSEN (D9:A)**

The first of {cve, sbom} to need the image triggers one `regctl image copy` into a per-run
OCI layout; both syft and grype then read `oci-dir:<layout>` instead of the remote ref, in
parallel. Removes syft's AND grype's pulls (2 of 4). syft/grype natively support
`oci-dir:`, so no per-tool plumbing. Effort **M**, risk **Low**, verified above.

## Recommended Approach: D

Captures the dominant (pull) cost for the two tools that read a local layout cleanly, at M
effort, with empirical proof. It is the correct _primitive_ — Approach C extends it to
trufflehog/dockle with no rework, unlike the SBOM-handoff which C would have thrown away.

### Mechanism

`CachingToolRunner` decorator (sibling of `CachingImageInspector`), built once per `run()`,
wrapping the delegate `ToolRunner`:

- Memo keyed by **full image ref** → value = a per-run OCI layout dir for that ref.
- First `scan_vulnerabilities` or `generate_sbom` with sharing on triggers
  `regctl image copy --platform <p> <ref> ocidir://<tmpdir>` **once**; the lock is held
  across the export so the second tool waits and reuses the layout (same lock-across-call
  idiom as part 1). Note: the lock is across the _export only_ — syft and grype then run
  in **parallel**, no serialization.
- `generate_sbom(image)` → `syft oci-dir:<tmpdir>` (cyclonedx, as today). `scan_vulnerabilities(image)`
  → `grype oci-dir:<tmpdir>`. Both produce byte-identical output vs the remote ref
  (verified: 477 components, 365 CVEs).
- **Fallback:** if `regctl image copy` fails, both fall back to the remote `<image>` ref
  (today's behavior) — an export failure never breaks a scan.
- **No SBOM handoff (D10):** grype catalogs the layout itself, so it does not depend on
  syft's SBOM quality — the degraded-SBOM hole (old D5) evaporates. Replacing `grype oci-dir:`
  with `grype sbom:` to save grype's re-catalog is a deferred CPU optimization (see NOT in scope).
- `share_sbom` gate = `_CVE in selected and _SBOM in selected` (named module constants,
  eng-review D8 — not inline literals). A single-analyzer run gains nothing from export
  (1 export + 1 local read ≈ 1 direct pull), so the gate stays on both-selected. `run_one`
  is a pure pass-through (eng-review D3).

Delegate (`SubprocessToolRunner`) gains: a `regctl image copy` wrapper (extend
`regis/utils/regctl.py`) and an "oci-dir source" variant of `run_syft`/`run_grype` (the ref
arg becomes `oci-dir:<path>`; no registry auth, no `--platform` — the layout is one platform).

### Wiring (same injection philosophy as part 1)

The concrete `CachingToolRunner` is built in the **composition root** (where part 1 builds
`CachingImageInspector`), injected into `AnalyzeImage` as a callable
`Callable[[ToolRunner, bool], ToolRunner]`, so `core/` stays import-linter-clean.

- `run()` builds the decorator once with `share = (_CVE in selected and _SBOM in selected)`,
  captures it in the worker closure, passes it into `_dispatch` (which gains a `tools` param
  and no longer reads `self._tools`, `analyze_image.py:105`). One decorator serves the whole
  `run()` even across images (memo keyed by ref).
- `run_one()` passes `self._tools` straight through (no wrap, no `close()`).
- Cleanup (eng-review D6): the OCI layout lives in a `tempfile.TemporaryDirectory` owned by
  the decorator; `run()`'s `finally` calls `tools.close()`, idempotent
  (`TemporaryDirectory.cleanup()` tolerates a second call). The `with ThreadPoolExecutor`
  block joins **before** the `finally`, so no tool is still reading the layout when removed.

## What already exists (reused, not rebuilt)

- `CachingImageInspector` (part 1) — decorator + lock-across-call idiom; `CachingToolRunner` mirrors it.
- `regis/utils/regctl.py` — regctl wrappers (extend with `image copy`); regctl already a dependency.
- `SubprocessToolRunner._full_ref` — the ref string; reuse for the memo key.
- The `inspector_factory` injection seam in `_dispatch` — the shape the `tools` param mirrors.

## NOT in scope (considered, deferred)

- **SBOM handoff (`grype sbom:`)** — saves grype's re-catalog CPU, but the data says the
  bottleneck is pull (network), not catalog (CPU). Deferred until a central scan proves
  cataloging-bound. Composes on top of this layout with no rework.
- **Approach C — trufflehog + dockle on the local layout** — removes the 3rd/4th pull but
  needs per-tool local-input plumbing (dockle `--input` tar, trufflehog docker-archive).
  Verify those sources, then extend. Higher bandwidth win, separate PR.
- **`oci.py` nested ThreadPool** (P3, per the ticket).
- **Capability-based SBOM gate** (`consumes_sbom`/`produces_sbom`) replacing the name
  constants (eng-review D8 follow-up).
- **Distribution / CI** — behavior change in the shipped `regis` CLI, none needed.

## Success Criteria

1. **Perf:** `regis analyze` wall-clock on a large image with cve+sbom enabled drops
   measurably (T1 baseline 72.9s; syft+grype pair ~53s→~30s projected).
2. **Two pulls → one:** assert exactly one `regctl image copy` and **zero** standalone
   `syft <image>` / `grype <image>` pulls when both run (both read `oci-dir:`).
3. **CVE non-regression (gate):** on an OS-package image (`debian:*-slim`), grype's CVE id
   set from `oci-dir:` equals `grype <image>`, **`--platform`-pinned on both sides**
   (eng-review D4) for determinism. (Verified once already: python:3.12, 365 = 365.)
4. **SBOM non-regression:** syft's cyclonedx from `oci-dir:` equals `syft <image>` (component
   count + purls) on the same fixture.
5. **Failure isolation:** a forced `regctl image copy` failure → both tools fall back to the
   remote ref, valid reports still produced.
6. **No layout leak:** `close()` removes the temp layout; idempotent; no leak if `run()` raises.

## Failure modes (per new codepath)

| Failure                                  | Test?                         | Handling                                   | User-visible?                |
| ---------------------------------------- | ----------------------------- | ------------------------------------------ | ---------------------------- |
| `regctl image copy` fails (auth/network) | Criterion 5                   | Fallback to remote `<image>` for both      | Yes — reports still produced |
| layout leak / double `close()`           | Criterion 6                   | `TemporaryDirectory.cleanup()`, idempotent | No (internal)                |
| platform drift export↔scan               | Criterion 3 (platform-pinned) | layout is one platform                     | No (test gate)               |

No failure mode is silent-and-untested-and-unhandled → **no critical gap.**
